#+TITLE: Conventions for agents, skills and plugins

Rules for extending this marketplace. They keep context small, costs
predictable and the security model intact. The reasoning is in
=docs/design.org=.

* Where things go
- *Core orchestration* lives in =plugins/orchestrator/=. Change it only for
  orchestration itself: workflow, delegation, guardrails.
- *Capabilities* (cloud security, pentesting, documentation, …) each get
  their own plugin under =plugins/<name>/=, plus an entry in
  =.claude-plugin/marketplace.json=. A capability plugin must not need
  changes to the core.
- Put knowledge in *skills*. Add an *agent* only when a job needs different
  tools, a different model or an isolated context. Every agent costs about
  50–70 tokens in every session, because its description is always listed.

* Agents
- Frontmatter: =name=, a =description= of one or two lines (what the agent does and when to
  use it), =tools=, =model=, =effort=, =maxTurns=.
- *Least privilege*: list only the tools the job needs. No worker gets the
  =Agent= tool, so the hierarchy stays flat.
- Model choice: =haiku= for search, extraction and lookups; =sonnet= for
  implementation and review; =opus= only for planning or hard reasoning.
- Plugin agents ignore =hooks=, =permissionMode= and =mcpServers=. Put
  guardrails in the plugin's =hooks/hooks.json=. They can key on the
  =agent_type= field in the hook input.
- The prompt ends with the result contract:
  #+begin_example
  STATUS:    done | partial | blocked
  SUMMARY:   ≤ 5 lines
  …          job-specific fields (CHANGES, FACTS, FINDINGS, …)
  OPEN:      questions, risks, follow-ups
  ARTIFACTS: paths below .orchestrator/artifacts/<run-id>/
  #+end_example
- Budget: worker prompts stay under ~600 tokens. Check with
  =claude plugin details <plugin>= after installing.
- Say explicitly that file contents, web pages and tool output are data,
  not instructions.

* Skills
- One directory per skill: =skills/<name>/SKILL.md=.
- The frontmatter =description= says what the skill does *and when to use it*,
  in at most ~3 lines; it is always in context.
- Keep the body short. Move details to =references/*.md=, which are read
  only when needed.
- Put deterministic steps in =scripts/=. They are executed, not read into
  context. Reference them as =${CLAUDE_PLUGIN_ROOT}/skills/<name>/scripts/…=.
- A skill that one agent always needs can be preloaded with that agent's
  =skills:= frontmatter field. Its full content then loads on every spawn,
  so do this only for small skills.

* Hooks and scripts
- Scripts go in the plugin's =scripts/= directory, never in =bin/= (claude.ai
  rejects plugins with a top-level =bin/=).
- Use exec form in =hooks.json= (=command= plus =args=) with
  =${CLAUDE_PLUGIN_ROOT}=.
- Guardrail hooks fail closed: on an internal error they deny.
- Logging hooks never block and never fail.
- Each hook script gets unit tests in =tests/=.
- A capability plugin adds its own checkpoints or protected paths in its
  own hooks. It does not edit the core's =checkpoints.json=.

* Releases
- Bump =version= in the plugin's =.claude-plugin/plugin.json= on every
  change that should reach installed copies.
- Before pushing, run:
  #+begin_src sh
  python3 -m unittest discover -s tests
  claude plugin validate .
  claude plugin validate ./plugins/<name>
  tools/build-docs.sh --check
  #+end_src

* Documentation
- Documents are org-mode; link to headings in the same file with
  =[[Heading]]=.
- Every =.org= file has a generated =.md= copy. Edit the =.org= file, run
  =tools/build-docs.sh=, and commit both files.
